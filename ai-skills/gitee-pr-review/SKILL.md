# Gitee PR Review

对用户给出的 Gitee PR URL（或项目、PR IID）做只读评审。默认只评审最新一轮 review 意见；用户明确要求时才扩大到历史意见或全部讨论。

## 获取证据

1. 从 URL 解析 `project_id`（`owner/repo`）和 PR IID。
2. 优先使用 Gitee MCP 的只读接口：
   - `get_enterprise_pull_detail`：目标/源分支、提交、作者、状态等；
   - `get_enterprise_pull_diff`：逐文件 patch；
   - `list_enterprise_pull_comments`：评论及 inline 位置。分页取完后再筛选。
   当前企业连接若需要固定参数，使用 `enterprise_id=13428393`（ymatrix）；不要把令牌写入技能或回答。若环境提供非 enterprise 的 Gitee MCP，使用其等价只读接口。
3. 按评论的 review/round 标识、提交 SHA 和时间判断最新一轮；有明确 review 标识时取最新 review 的全部意见（包括该轮 inline 评论和必要的 thread 上下文）。没有 round 元数据时，取时间最新的一组 review 评论，并说明判定依据；不能把普通 PR 讨论误称为 review。
4. 评审每条意见前，读取 diff 对应上下文及当前工作树中的相关代码；必要时追踪直接调用链。不要凭评论文字或函数名推断行为。

## 逐条判断

每条意见都给出：

1. **意见**：保留原意，附 `文件:行号`、作者和时间（若有）。
2. **是否成立**：`成立`、`部分成立`、`不成立` 或 `待确认`，说明能复核的代码/patch 证据。给出分析时必须写上可对照的代码位置：当前工作树里的 `文件`、函数名，以及行号或行范围。评论行号和当前代码不一致时，以当前代码为准，并注明评论指向的位置。不要只写函数名或只复述结论。
3. **实际重要性**：`阻塞`、`高`、`中`、`低`；按真实用户影响、数据正确性、崩溃/安全、兼容性和可回滚性判断，不按措辞或作者身份判断。不判断问题是否由当前提交或当前分支引入，也不据此降低重要性或改变处置。
4. **修复建议**：给出最小、可执行的方向和需要补的测试；只提出建议，不擅自修改代码或在 Gitee 回评。

### 重要问题的专项说明

对实际重要性为“阻塞”“高”或“中”的意见，不能只复述结论。除上述四项外，必须补充以下内容：

5. **核心逻辑**：结合当前工作树和 PR diff，说明相关函数的调用链、关键状态/长度/容量不变量，以及意见所描述的输入如何到达风险点；若意见不成立，要指出具体的前置校验、类型约束或调用方保证。
6. **处置建议**：明确给出“修复”“部分修复”“不采纳”或“待确认”，并说明最小改动位置、兼容性影响和验证用例。
7. **理想做法**：说明这条意见对应的目标行为和不变量，以及所述输入应在哪一层被处理。它描述正确的端到端结果，可以比最小改动更完整；最小改动仍写在修复建议和处置建议里。用目标行为表述，不要用“不要做某事”代替。

重要问题若判定为“不成立”或“不采纳”，仍需给出上述核心逻辑和理想做法，避免把“不同意”写成无证据的结论。低重要性或纯测试覆盖建议可沿用四项格式，但仍需给出可执行的测试方向。

按重要性从高到低编号；同级按文件路径、行号稳定排序。没有可评审的最新 review 时，明确报告“未找到”，不要编造意见。结尾简述证据边界、未验证项和是否建议阻塞合入。
