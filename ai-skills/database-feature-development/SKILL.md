# Database Feature Development

用于把大型数据库 feature 从多轮需求讨论推进到可评审、可验证、可交接的实现。流程不预设 feature 是索引、优化、存储、事务或运维能力；所有检查项都应按具体 feature 裁剪。

需要形成阶段说明、任务表或 checkpoint 时，读取 [references/phase-guide.md](references/phase-guide.md)。

## 工作状态

始终维护一份简短状态：

~~~text
当前阶段与收敛目标
最新确认基线
本阶段采用的用户输入
当前提案与待确认项
明确排除项
下一步
~~~

重要信息分为：用户结论、源码事实、当前提案、待验证假设、已否决方向。用户最新修正覆盖旧结论。“继续”只表示继续当前阶段，不自动批准未确认设计或扩大范围。

范围、框架、接口发生实质变化时更新基线版本，例如 Scope v2、Framework v1、Interface v3。实现、测试和 review 都引用最新基线。

每阶段开始时主动回显相关用户输入和收敛目标；结束时记录已收敛内容、延期项和未知项，并主动提示下一阶段需要用户确认的输入。

## 按 feature 选择分析维度

先判断哪些性质会影响当前设计，再选择检查维度。可考虑可见性、状态权威性、执行时机、模块归属、持久性、分布式职责、并发、恢复、兼容和可观测性；它们只是候选，不是固定分类。只保留会改变设计、代码边界或验收标准的维度。

## 阶段

| 阶段 | 收敛目标 | 确认要求 |
|---|---|---|
| 1. 范围 | 问题、边界、完成层次和验收标准稳定 | 重大范围决定需用户确认 |
| 2. 框架 | 职责、状态流、生命周期和异常行为统一 | 框架需用户确认 |
| 3. 接口 | 关键契约足以判断代码形态并安全拆任务 | 接口需用户确认 |
| 4. 任务拆分 | 形成依赖有序、可独立验收的任务 | 回显首条路径和延期项 |
| 5. 实现 | 代码符合最新接口和目标完整度 | 偏离基线时回退确认 |
| 6. 验证与 review | 行为、目标路径和限制均有证据 | 区分实测、推断和缺口 |
| 7. 交付与交接 | 得到可评审结果或精确续作点 | 报告仓库状态和残余风险 |

## 1. 范围确认

先回溯本 session 的目标、追问、纠正和已否决方案，不只总结最后一条消息。

确认：

- 具体触发场景和目标行为；
- 相关对象、角色、模块和生命周期路径；
- 允许与禁止修改的边界；
- 当前 feature 实际涉及的正确性、性能、兼容和运维要求；
- 本轮交付层次与长期目标的区别；
- 明确排除项和验收证据。

本阶段不锁死类名和函数签名。输出紧凑的 in-scope、out-of-scope、待确认项和 Scope 基线，然后主动进入框架确认。

## 2. 框架确认

覆盖所有适用的生命周期路径；只有 feature 确实存在生产者和消费者时才要求读写双向设计，不为填模板发明路径。

明确：

- 决策位置、状态权威来源和组件职责；
- 正常流程以及影响正确性的失败、回退和清理流程；
- 适用的事务、并发、恢复、分布式和兼容关系；
- 共享设施与 feature 专属逻辑的边界。

优先复用现有完整机制的最薄适配。新增抽象、重复校验或第二份 metadata 必须说明它消除的实际复杂度。公共代码中的设施也要按语义判断是否真正通用。

输出紧凑组件图或流程图，走通正常路径和关键异常路径，形成 Framework 基线。

## 3. 接口确认

对关键类型和函数说明职责、调用者、输入输出、ownership、生命周期、错误语义及适用的锁或事务前提。按 feature 展示初始化、正常使用、reset/rescan、失败、清理和共享状态路径。

强约束：

- metadata 尽量只有一个权威来源；
- 新类必须由状态、生命周期、不变量或实质复用支撑；
- 继承用于真实的可替换关系，否则比较 alias、组合、provider 或 adapter；
- 修改公共接口前，比较直接替换、wrapper、overload 和 adapter 的表达能力、调用点、兼容性及长期复杂度；
- 不保留无法正确表达新状态的兼容入口；
- 持久化状态要同时定义 writer、reader、发布、验证、兼容和恢复；
- 并行或共享状态要定义分配、传递、同步、重置和销毁。

输出关键声明或伪码、必要的所有权图、文件职责和有依据的工作量估算，形成 Interface 基线。

## 4. 任务拆分

按职责、依赖和端到端行为拆分，不按文件机械拆分。优先选一条能验证框架的完整垂直路径，同时说明它证明什么、延期什么、后续路径能否复用当前契约。

每项任务记录依赖、完成行为、排除项、验证证据、复杂度和回退阶段。用户要求的完成层次是停止条件：结构原型不能宣称完整，完整 feature 也不能停在可编译骨架。

## 5. 实现

只实现最新基线：

- 复用已有算法和工具，避免简化复制；
- 新概念必须能追溯到已确认设计；
- 抽取或移动代码时保留算法注释、锁和错误边界；
- 避免无意义参数、签名变化、代码移位、宽泛格式化和相邻清理；
- 注释解释长期原因和不变量；
- 每完成一条路径就检查 diff，清除本次引入的偶然复杂度。

进度更新说明已贯通路径、剩余缺口、基线偏差和下一项证据。编译通过只是检查点。

## 6. 验证与 review

验证从当前验收边界推导。优先测试 feature 的真实流程；当 fallback 也能返回正确结果时，应在可行范围内证明目标路径确实执行。用户要求最小测试时，不建立成本更高的测试框架。

分别报告：

- 实际运行并通过的命令；
- 仅由源码推断的行为；
- 未验证要求；
- 环境限制。

review 按当前 feature 选择风险维度，例如架构重复、正确性、资源生命周期、并发、持久化与恢复、兼容、性能保护、可观测性、路径激活和 diff 质量。不能发现一个表面问题后就结束。能力差异标为有意限制、缺失实现、架构限制或证据缺失。

## 7. 交付与交接

交付说明行为变化、设计偏差、实际验证、延期能力、残余风险和仓库状态。保护用户既有修改和未跟踪文件；外部写操作遵循已有授权。

长 session 可在 compact 前直接写 checkpoint。记录 worktree、branch、base/HEAD、tracked/untracked 状态、最新三类基线、完成内容、当前阶段、关键入口、实际测试、后台任务、剩余工作和新 session 首条提示词。恢复时先核对磁盘、进程和日志，不能把 checkpoint 当成当前事实。

## 回退确认条件

出现以下变化时，回到最早受影响的阶段：

- 问题、验收边界或交付层次改变；
- 职责、状态权威来源或生命周期改变；
- 需要第二份 metadata、持久化格式或公共契约；
- 延期能力推翻当前接口；
- 代码量或复杂度显著超过估算；
- 错误、回退、恢复或兼容语义不再成立；
- 原计划复用的机制无法承担所需语义。

已由基线覆盖的普通实现选择不重复请求确认。
